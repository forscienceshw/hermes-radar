# 01 · 技术原理

本文件回答：微信 4.2 的库到底怎么加密的、密钥从哪来、为什么必须合并 WAL、表是怎么组织的。
全部结论都在 Windows 11 + 微信 4.2.0.53 上实测过，不是推测。

---

## 1. 数据在哪

```
数据根   %APPDATA%\Tencent\xwechat\config\<hash>.ini      ← 纯文本，里面就一行路径
         （也可能在 HKCU\Software\Tencent\Weixin\FileSavePath，
          但本机实测注册表里只有 InstallPath，路径在 ini 里）

实际布局 <数据根>\xwechat_files\<wxid>_<4位>\db_storage\
           contact\contact.db          联系人 + 公众号目录（biz_info）
           message\message_0.db        私聊（按会话分表）
           message\biz_message_0.db    公众号 / 服务号（按会话分表）
           message\message_fts.db      全文索引（不读也无所谓）
           session\session.db          会话列表
           favorite\favorite.db        收藏
           sns\sns.db                  朋友圈
           …共 20 个 .db，每个旁边都有 -wal / -shm
```

判据：`<数据根>` 下同时存在 `xwechat_files` 和 `all_users`。
实测本机是 `D:\program\WeixinDocument`，从 `%APPDATA%\Tencent\xwechat\config\*.ini` 读到。

## 2. 加密结构（SQLCipher 4）

| 项 | 值 |
|---|---|
| 页大小 | 4096 |
| 加密 | AES-256-CBC，**逐页独立 IV** |
| 保留区 | 每页末尾 **80 字节** = 16 字节 IV + 64 字节 HMAC-SHA512 |
| salt | **只**在第 1 页最前面 16 字节 |
| 密钥长度 | 32 字节（内存里以 64 位十六进制字符串形式出现） |
| KDF | 见下面第 3 节的"重要发现" |

页 1 布局：

```
[0:16]            salt
[16 : 4096-80]    密文（4000 字节）
[4096-80 : 4096-64] IV（16 字节）
[4096-64 : 4096]  HMAC-SHA512（64 字节，覆盖 [16:4096-64] + 页号LE32）
```

其它页：

```
[0 : 4096-80]     密文（4016 字节）
[4096-80 : 4096-64] IV
[4096-64 : 4096]  HMAC（覆盖 [0:4096-64] + 页号LE32）
```

解密第 1 页时跳过前 16 字节 salt，输出时补回 `SQLite format 3\0` 头；保留区填 0。

mac_key 的派生（SQLCipher 4 规范）：

```python
mac_salt = bytes(b ^ 0x3A for b in salt)
mac_key  = pbkdf2_hmac("sha512", enc_key, mac_salt, 2, dklen=32)
```

**HMAC 是唯一可靠的验证手段。** 密钥错的时候 AES 解出来是垃圾但不会报错，只有 HMAC 对不上。

## 3. 密钥从哪来（本模块的核心）

### 3.1 老办法为什么失效

微信 3.x / 4.0 会把 `x'<64位hex>'` 明文缓存在进程内存里，扫字符串就行（`analysis/wechatmsg_full`
那套）。**4.1 之后不再明文缓存**。实测证据：`Weixin.exe` 主进程 1.1 GB 可读内存里，
`x'<64hex>'` 命中 **0** 次。

### 3.2 现在的藏法

密钥在 WCDB 的配置对象里，数据块被**固定掩码异或**过。

```
掩码（29 字节）：
d2c7442458020000004889442450488b 450048844c2448488944254048584c24
```

回溯路径（全部小端）：

```python
# 1. 全内存找字符串 needle = b"com.Tencent.WCDB.Config.Cipher" 的所有地址
needle_addrs = find_all(handle, CIPHER_NAME)

# 2. 找 [ptr=needle_addr][len=len(needle)] 这对 8+8 字节 —— 这是个 C++ string 对象引用
pattern = struct.pack("<Q", addr) + struct.pack("<Q", len(CIPHER_NAME))

# 3. 命中位置 qaddr；节点从 qaddr-0x10 开始
node = read(handle, qaddr - 0x10, 0x50)

# 4. 自校验，防误命中
assert u64(node, 0x10) == addr            # name 指针
assert u64(node, 0x18) == 28              # len(b"com.Tencent.WCDB.Config.Cipher")

# 5. 配置对象
config_ptr = u64(node, 0x28)
obj   = read(handle, config_ptr + 0x88, 0x28)
data_ptr = u64(obj, 0x8)                  # 数据块地址
data_len = u64(obj, 0x10)                 # 99 或 96 之类，<= 1024

# 6. 异或还原
blob   = read(handle, data_ptr, data_len)
plain  = bytes(b ^ MASK[i % len(MASK)] for i, b in enumerate(blob))

# 7. 形如  x'<64位hex 密钥><32位hex salt>'
m = re.search(rb"x'([0-9a-fA-F]{64,192})'", plain)
```

**重要发现（与部分公开资料不一致，但实测 20/20 成立）：**
那 64 位十六进制**就是最终的 AES-256 密钥本身**，不是需要再跑 256000 轮 PBKDF2 的 passphrase。
判断依据：直接用它对第 1 页算 2 轮 PBKDF2 派生 mac_key 就能验过 HMAC；如果它还是 passphrase，
HMAC 不可能过。所以解密路径上**没有** 256000 轮 KDF，速度快得多。

每个库一把独立的钥匙（因为每库 salt 不同）。实测 20 个库 → 20 个不同的 (key, salt) 组合。

### 3.3 容错

内存里可能同时存在旧会话的候选。所以取到候选后**必须逐库用 HMAC 验**，验过的才用。
候选数量通常 20~25 个，全部检查一遍不到 1 秒。

## 4. 为什么必须合并 WAL

微信是 WAL 模式。**主库文件会滞后**——实测滞后 109 秒（主库最新消息 00:54:27，当时 00:56:16）。
不合并 WAL，用户会觉得"雷达漏了新消息"。

WAL 格式（全部**大端**）：

```
32 字节头： magic(4) version(4) pagesize(4) checkpoint_seq(4) salt1(4) salt2(4) cksum1(4) cksum2(4)
           magic ∈ {0x377f0682, 0x377f0683}；pagesize 实测 4096

每帧：     24 字节帧头 + 4096 字节页
           帧头 = pgno(4) dbsize(4) salt1(4) salt2(4) cksum1(4) cksum2(4)
```

合并算法：

```python
committed, commit_size, pages = {}, 0, {}
for frame in frames:
    pgno, dbsize, salt1, salt2 = unpack(">IIII", hdr)
    if (salt1, salt2) != (wal_salt1, wal_salt2): break   # ← 关键：跨代残留帧，必须停
    if not page_hmac_ok(mac_key, page, pgno):    break   # ← 关键：半截写或错页，必须停
    pages[pgno] = decrypt_page(page, pgno)
    if dbsize:                                   # 这是一个提交点
        committed, commit_size = dict(pages), dbsize

total = commit_size or main_pages                     # 以最后一次提交的页数为准
out   = [ committed.get(pgno) or decrypt_main_page(pgno) for pgno in 1..total ]
```

**为什么第 1 条判断不能省**：跨 checkpoint 的残留帧，内容仍是合法密文、HMAC 也验得过
（mac_key 只跟库的 salt 有关，不随 WAL 代次变），但它是旧版本页。混进来 →
`PRAGMA integrity_check` 报 `invalid page` / b-tree 结构错乱。实测不校验 salt 时有 12/20 个库损坏。

**WAL 页的加密布局和主库页一样**，包括第 1 页前 16 字节也是该库的 salt（实测一致）。

## 5. 表结构（4.2 按会话分表）

```
message_0.db        私聊：146 张 Msg_* 表
biz_message_0.db    公众号/服务号：706 张 Msg_* 表
```

- **表名 = `Msg_` + md5(user_name)**（小写十六进制）。
  实测 md5 与 md5_gbk 都对，sha1/sha256/md5-utf16 全不对。
  验证：10515 个候选中 852 个命中。
- `Name2Id(user_name)` 给反查用（表名 → 会话）。
- 消息表列：
  `local_id, server_id, local_type, sort_seq, real_sender_id, create_time, status,
   upload_status, download_status, server_seq, origin_source, source, message_content,
   compress_content, packed_info_data, WCDB_CT_message_content, WCDB_CT_source`
- `local_type` 高位是标志位：`local_type & 0xFFFFFFFF` 才是类型。
  **49 = 公众号/应用消息**（实测值形如 `21474836529 = 0x500000031`）。
- `create_time` 是秒级 Unix 时间戳。
- **正文是 zstd 压缩的**，标记在 `WCDB_CT_message_content`，实测值 **4**（不是文档里常写的 1），
  魔数 `28 b5 2f fd`。`source` 列同样压缩（`WCDB_CT_source = 4`）。

文章卡片的正文是 XML：

```xml
<msg><appmsg appid="" sdkver="0">
  <title><![CDATA[标题]]></title>
  <des><![CDATA[摘要]]></des>
  <url>https://mp.weixin.qq.com/s?__biz=...&amp;mid=...&amp;idx=...&amp;sn=...&amp;chksm=...&amp;scene=1&amp;srcid=...</url>
  <type>5</type>
</appmsg></msg>
```

**`<url>` 里的 `&amp;` 要先还原成 `&`；`chksm` 等参数要原样保留**（见 `03-踩坑清单.md` 第 1 条）。

## 6. 公众号目录

`contact/contact.db`：

```sql
SELECT username, remark, nick_name, alias FROM contact WHERE username LIKE 'gh_%'
-- 本机 10509 条联系人，其中 1706 个 gh_
```

名字优先级建议：**remark > biz_info.brand_info 里的 nick_name/brand_name > nick_name > alias > username**。
`contact.nick_name` 经常是空的，真实品牌名常在 `biz_info.brand_info`（JSON 字符串）里。

## 7. "自己转发的链接"在哪里

不是单独的库，就是**自己 wxid 的那张会话表**（`message_0.db` 里 `Msg_<md5(自己的wxid)>`），
外加 `filehelper`（文件传输助手）。里面 `local_type&0xFFFFFFFF == 49` 且含
`mp.weixin.qq.com` 的，就是自己转发过来的文章。

自己的 wxid 从数据目录名推：`<wxid>_<4位数字>` → 去掉 `_NNNN` 后缀。

## 8. 其它平台（供参考，未实测）

- macOS：库在 `~/Library/Containers/com.tencent.xinWeChat/Data/.../db_storage`，
  密钥同样要从进程内存取，但进程名和对象布局不同。
- Linux：有公开的 GDB 断点法（在密钥计算函数上下断点读寄存器），思路不同。
- 本模块的读取端（表映射、zstd、WAL 合并）是跨平台的，**只有"取密钥"这一步是 Windows 专用**。
  如果目标机器不是 Windows，需要替换 `scan_keys()`，其余可复用。

## 9. 性能实测（本机，i5 级 CPU）

| 操作 | 耗时 |
|---|---|
| 扫内存取密钥（1.1 GB / 5 个进程） | 约 20 秒（首次）；之后用缓存 0 秒 |
| 全量解密 + WAL 合并 20 个库（99 MB） | 4.4 秒 |
| 增量（只重解变化的库） | 0.3~2 秒 |
| 抽取近 30 天文章链接（151 篇） | 约 1 秒 |
