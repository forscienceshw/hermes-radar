# 03 · 踩坑清单

每条都是真踩过的，格式统一：**症状 → 原因 → 正确做法**。按"会让整条链路白干"的程度排序。

## 坑 1 ★★★★★ 把文章链接的 query 参数裁掉，微信就返回滑块验证页

**症状**

- 归档任务全部失败，错误信息是"微信返回验证页或非正文页面"
- 抓回来固定约 **17,692 字节**，内容里没有 `js_content`，而是 `captcha` / `TCaptcha` / `cgiData`
- 换成真浏览器（headless Edge，走完整个 JS）也一样被挡
- 换网络、换 IP、挂代理都"看起来没用"
- **但同一篇文章在另一个电脑上能正常归档**

**原因**

微信公众号卡片的 `<url>` 长这样：

```
https://mp.weixin.qq.com/s?__biz=...&mid=...&idx=...&sn=...&chksm=...&mpshare=1&scene=1
                              &srcid=...&sharer_shareinfo=...&sharer_shareinfo_first=...#rd
```

为了去重，很容易把这些参数"规范化"成 `__biz&mid&idx&sn`。**微信现在会校验 `chksm` 等参数**——
参数不全的请求会被判定成爬虫，直接给腾讯云滑块验证页，而不是文章。

**决定性对照实验（同一篇文章、同一时刻、同样请求头，只改链接）**

| 链接 | 结果 |
|---|---|
| 完整原始链接 | HTTP 200，**3,616,258 字节**，有 `js_content`，正文完整 |
| 裁成 `__biz/mid/idx/sn` | HTTP 200，**17,692 字节**，`TCaptcha` 滑块页 |

脚本见 `tools/repro_url_param.py`，30 秒出结果。

**正确做法**

```python
# 抓取用原始链接；去重才用规范化链接。两个字段，两个用途。
url      = raw_url_from_xml.replace("&amp;", "&")     # 原样保留全部参数
canonical = canonical_url(url)                        # 只取 __biz/mid/idx/sn，仅用于去重
```

入库时：`items.url = url`（原始），`items.canonical_url = canonical`（去重键）。
**归档器必须拿 `items.url` 去抓，不能拿 `canonical_url`。**

> 我上一轮就是在这里翻车：把 4.x 适配器里的 `url` 字段直接写成了规范化结果，
> 于是"归档全部失败"，并被误判成"IP 被风控、只能换网络"。实际问题是我自己抹掉了指纹。

## 坑 2 ★★★★☆ XML 里的 `&amp;` 没还原

**症状**：URL 里带着 `&amp;mid=` 这种字符串，请求报错或返回"参数错误"（约 31 KB 页面）。

**原因**：消息正文是 XML，`<url>` 里的 `&` 被转义成 `&amp;`。

**正确做法**：解析出来后先做 `url.replace("&amp;", "&")`，再 `replace("&quot;", '"')`、
`replace("&lt;", "<")`、`replace("&gt;", ">")`，`rstrip("&,;)")`。

## 坑 3 ★★★★☆ 合并 WAL 不校验帧 salt，会把库拼坏

**症状**：`PRAGMA integrity_check` 报 `invalid page` / b-tree 结构错乱；12/20 个库中招；
但每个单独的页 HMAC 都能验过，看起来"密钥是对的"。

**原因**：WAL 里会残留**上一代 checkpoint** 的帧。那些页仍是合法密文，HMAC 也验得过
（`mac_key` 只跟库的 salt 有关，跨代不变），但内容是旧版本。按"最后一帧提交点"简单合并
就会把新旧页混在一起。

**正确做法**：两条判断都要，任一不满足立即 `break`，后面的帧全丢：

```python
if (frame_salt1, frame_salt2) != (wal_salt1, wal_salt2):
    break                     # 跨代残留帧
if not page_hmac_ok(mac_key, page, pgno):
    break                     # 半截写 / 错页
```

再取**最后一次提交**的 `dbsize` 作为总页数（`commit_size`），不要用 `max(pgno)`。

## 坑 4 ★★★☆☆ zstd 的压缩标记是 4，不是 1

**症状**：正文全是空字符串；`message_content` 有几千字节的 blob，但解出来是空的。

**原因**：`WCDB_CT_message_content` 实测值是 **4**（不少资料写的是 1）。

**正确做法**：同时认 `{1, 4}`，并且**优先看魔数**：

```python
ZSTD_MAGIC = b"\x28\xb5\x2f\xfd"
if blob[:4] == ZSTD_MAGIC or flag in {1, 4}:
    zstandard.ZstdDecompressor().decompress(blob, max_output_size=64 << 20)
```

另外 `decompress` 要兼容 `stream_reader`（有些块是流式写的，一次性 `decompress` 会失败）。
**`zstandard` 没装的话，正文会静默变成空字符串**——这也是最容易误判的时刻。

## 坑 5 ★★★☆☆ `local_type` 高位是标志位

**症状**：按 `type == 49` 过滤，一条公众号文章都匹配不到。

**原因**：实测 `local_type` 值是 `21474836529` 这种（`0x500000031`），高位带标志。

**正确做法**：

```python
base = int(local_type) & 0xFFFFFFFF      # 49 = 公众号/应用消息
```

## 坑 6 ★★★☆☆ 表名是 md5，不是 sha1

**症状**：`Msg_<hash>` 一张都对不上。

**原因**：表名 = `"Msg_" + md5(user_name)`，小写十六进制。
`md5_gbk` 也巧合能对（因为 username 全是 ASCII），但 `sha1[:32]` / `sha256[:32]` /
`md5(utf-16-le)` 全都不对。

**正确做法**：

```python
"Msg_" + hashlib.md5(username.encode("utf-8")).hexdigest()
```

## 坑 7 ★★★☆☆ `db.one()` 会自动追加 `LIMIT 1`

**症状**：`sqlite3.OperationalError: near "LIMIT": syntax error`。

**原因**：项目里的 `Database.one(sql)` 实现是 `query(sql + " LIMIT 1")`。

**正确做法**：传给 `db.one()` 的 SQL **不要自己写 `LIMIT 1`**。

## 坑 8 ★★★★☆ 前端顶层函数重名，整页点不动

**症状**：打开公众号库页面，控制台 `Cannot read properties of undefined (reading 'state')`；
统计卡片出来了，但表格一片空白，点什么都没反应。第一次进入时还不报错（被 `.catch` 吞了）。

**原因**：`app.js` 和 `setup.js` 各自声明了顶层 `function renderWechat(...)`。
两个都是 classic script，等价于 `window.renderWechat`，**后加载的 `setup.js` 覆盖了前者**。
于是 `app.js` 调自己的 `renderWechat()`（无参）时，执行的是 `setup.js` 那个，
里面读 `wechat.state` → 参数是 `undefined`。

**正确做法**：改名（`renderSetupWechat`）+ 把 `setup.js` 整体包进 IIFE，只导出必须的
`window.loadSetupPanel`。改名能治当下，IIFE 能治以后。

## 坑 9 ★★★☆☆ `available()` 依赖进程存在，微信一关就全线报错

**症状**：微信退出后，来源每条都报"微信电脑版未运行；首次同步需要登录并保持微信运行"，
`error_count` 一路涨到 30。

**原因**：判断"4.x 能不能用"时只看 `Weixin.exe` 是否在跑。但密钥已经缓存、库已经解密过，
微信关着反而更好读（文件不被占用）。

**正确做法**：

```python
def available() -> bool:
    status = quick_status()
    if status["running"] and status["storages"]:
        return True
    cache = DEFAULT_CACHE                       # DATA_DIR/wechat4
    if (cache / "keys.json").is_file():
        return any(p.is_file() for p in cache.rglob("*.db"))
    return False
```

注意：这样只能读到**上一次同步到的快照**。要拿新消息，微信必须开着（密钥在进程内存里）。

## 坑 10 ★★☆☆☆ 用 `reset_attempts=True` 就没法数重试轮次

**症状**：想"重试 3 轮就收尾"，但 `attempts` 永远是 0，判断永不触发。

**原因**：`reschedule_job(..., reset_attempts=True)` 会把 `attempts` 清零——它本来是给
"静默时段等待"用的，避免把等待算成失败。

**正确做法**：把轮次写进 `last_error` 前缀自己数：

```python
previous = str(job.get("last_error") or "")
seen = 0
if previous.startswith("微信验证 #"):
    seen = int(previous[len("微信验证 #"):].split("：", 1)[0].strip() or 0)
seen += 1
... reason=f"微信验证 #{seen}：{exc}"
```

## 坑 11 ★★☆☆☆ 公众号昵称经常是空的，品牌名在 `biz_info`

**症状**：同步出来的公众号一大半名字是 `gh_xxxxxxxx` 这种原始 id。

**原因**：`contact.nick_name` 对本机同步来的公众号经常为空。

**正确做法**：按 **备注(remark) > `biz_info.brand_info` 里的 `nick_name`/`brand_name` > nick_name >
alias > username** 的优先级取名，并把所有候选名放进 `aliases` 供模糊匹配。

## 坑 12 ★☆☆☆☆ 用 PowerShell 写 `settings.json` 会加 BOM

**症状**：程序把配置文件重命名为 `settings.json.broken-<timestamp>`，然后用默认值启动。

**原因**：PS 5.1 的 `Set-Content -Encoding UTF8` 写 BOM，JSON 解析器不认。

**正确做法**：用 Python `json.dump(..., ensure_ascii=False)` 写，或 `-Encoding utf8NoBOM`。
（程序这个"坏配置不崩、只隔离"的行为是对的，别改成崩溃。）

## 坑 13 ★☆☆☆☆ 别被控制台的乱码骗了

**症状**：`Get-Content settings.json` 显示 `"鐮旂┒"` 之类；`Invoke-RestMethod` 打印中文乱码。

**原因**：PowerShell 5.1 读 UTF-8 无 BOM 文件用 ANSI 解码；HTTP 响应没带 `charset` 时按 Latin-1 解。

**正确做法**：判断数据是否损坏要用 Python：

```python
json.loads(Path('config/settings.json').read_text(encoding='utf-8'))
```

HTTP 响应用 `-OutFile` 落地再用 UTF-8 读，或干脆用 venv 里的 Python `urllib` + `json`。

## 附：不需要的东西（别浪费时间）

- **不需要 `pymem`**：`ctypes` 直接调 `OpenProcess` / `VirtualQueryEx` / `ReadProcessMemory` 就够。
- **不需要管理员权限**：同用户进程实测可以直接读（`OpenProcess` 返回非零句柄）。
- **不需要 `sqlcipher3`**：自己按页解密成明文 `.db`，再用标准 `sqlite3` 读，反而更快更可控。
- **不需要注入 / hook / 改微信**：全程只读，不碰微信任何文件。

## 坑 14 ★★★☆☆ `t=pages/image_detail` 不是文章，永远归档不了

**症状**：一批条目长期停在「无法详细归档」，原因写着"微信返回验证页"，重试多轮也不变。

**原因**：公众号卡片里有一类链接长这样：

```
https://mp.weixin.qq.com/s?t=pages/image_detail&scene=1&__biz=...&mid=...&idx=1&sn=...&sharer_share...
```

这是"分享某张图片"的浏览器页（图片/视频分享页），不是文章正文页。
**完整链接也是 17.8 KB 验证码页**——因为那个端点本身就不返回文章 HTML，跟参数无关。

**怎么发现**：本机实测 146 条条目里 20 条是这种，其中 19 条状态是 `insufficient`，
而**非** `t=pages/` 的条目里 117 条 `ready`、只有 2 条 `insufficient`。一眼就能看出来。

**正确做法**：在归档入口按 URL 直接判定，不走网络、不占重试预算：

```python
class NotAnArticle(RuntimeError):
    """链接指向的不是文章正文（图片分享页 / 视频页 / 小程序页）。"""

# archive_web() 开头
if "mp.weixin.qq.com" in url and "t=pages/" in url:
    raise NotAnArticle("这是公众号的图片/视频分享页（链接里带 t=pages/），不是文章正文页，"
                       "无法归档；标题和链接已保留，可以直接点开看。")

# worker 里对 NotAnArticle 直接 force_dead + 条目标 insufficient
```

同时，**采集端不该把它当文章**。如果你想让库里干净，可以在 `article_of()` 里直接返回 `None`
跳过这类卡片；如果想保留链接，就按上面给它一个准确的"无法归档"理由——但**不要**写成
"被微信拦截"，那会让人往错误方向查。
