# 05 · 实测记录

所有数字都来自同一台真机，不是估算。目的是让接手的人知道"正常"长什么样，
以及哪些数字可以拿来对照。

## 1. 密钥提取

| 指标 | 值 |
|---|---|
| 扫描的进程 | 5 个 `Weixin.exe`（主进程约 1.13 GB 可读内存） |
| `x'<64hex>'` 明文命中 | **0 次**（老办法在 4.2 上完全失效） |
| `com.Tencent.WCDB.Config.Cipher` 字符串命中 | 1 次（**只是静态字符串表**，旁边全是 `Number of columns can not be zero` 这类日志文案，不是活对象） |
| 走对象回溯后拿到的候选 | 23 个 |
| 逐库 HMAC 验证通过 | **20 / 20** |
| 每个库一把独立密钥 | 是（20 个不同的 key/salt 组合） |
| 首次耗时 | 约 20 秒 |
| 之后（keys.json 缓存命中） | 0 秒 |

**判断"那 64 位就是最终密钥、不需要 256000 轮 PBKDF2"的依据**：只用
`PBKDF2-HMAC-SHA512(enc_key, salt^0x3a, 2)` 派生 mac_key 就验过了第 1 页 HMAC。
如果它是 passphrase，HMAC 不可能过。20/20 一致。

## 2. 解密与 WAL 合并

| 指标 | 值 |
|---|---|
| 全量 20 个库（99 MB） | **4.4 秒** |
| 增量（只解变化的库） | 0.3 ~ 2 秒 |
| `PRAGMA integrity_check` | 17 个 `ok`；3 个 `*_fts.db` 报 `SQL logic error`（FTS5 影子表老问题，不影响正文） |
| 主库滞后（未合并 WAL） | 约 **109 秒**（主库最新 00:54:27，当时 00:56:16） |

**WAL 坑的实测对照**：不校验帧 salt 时，**12 / 20 个库**在 `integrity_check` 报
`invalid page` / b-tree 结构错乱；加上 salt 校验 + 逐页 HMAC 后 **20/20 通过**。

## 4. ★ 链接参数的对照实验（本项目的关键数据）

同一篇文章、同一时刻、同一套请求头，**只改 URL 参数**：

| 链接 | HTTP | 字节数 | 判定 |
|---|---|---|---|
| 完整原始链接（含 `chksm`/`mpshare`/`scene`/`srcid`） | 200 | **3,616,258** | 正文 ✅ |
| 裁成 `__biz/mid/idx/sn` | 200 | **17,692** | 腾讯云滑块验证码 ❌ |

重复 4 条不同文章，全部同样结论（3,588,155 / 3,609,815 / 3,713,821 / 3,621,093 字节）。

滑块页里的关键证据：

```js
window.cgiData = {
    target_url : "https://mp.weixin.qq.com/s?__biz=...&mid=...&idx=...&sn=...",
    cap_appid  : "2003810213",
    cap_sid    : "10415532492569333361",
    poc_sid    : "HO3U-2qjHnBv80Q83Ni6AVkOLlQpj7z1Xikt0wg0",
    timeout_ms : "120000",
}
// 并加载 https://captcha.gtimg.com/TCaptcha.js
```

`target_url` 就是那篇文章——过完滑块才 302 过去。

**排除过的因素**（都不是原因）：

| 尝试 | 结果 |
|---|---|
| 先访问 `mp.weixin.qq.com` 首页拿 cookie（拿到 `ua_id`）再抓 | 仍是验证页 |
| 换 UA（Chrome / 微信内置 / 移动端） | 仍是验证页 |
| 加 `Accept` / `Accept-Language` | 仍是验证页 |
| `http` 而不是 `https` | 仍是验证页 |
| 真浏览器 headless Edge 走完 JS | 仍是验证页 |
| r.jina.ai / allorigins / corsproxy / codetabs 公共代理 | 超时 / 500 / 403 / 522 |
| 搜狗微信搜索（能搜到 18 条结果）→ 跟进 | 被搜狗自己的 antispider 拦 |

**结论**：不是网络被封、不是 UA、不是 cookie，是 query 参数完整性。

## 9. 大模型（与本模块无强耦合，供参考）

- WorkBuddy 点数模式是 `node` 子进程跑 `cloud/dist/llm-worker.mjs`，
  用**应用级 publicly key**（`wbpk_…`）+ 匿名会话，**不读本机 WorkBuddy 登录态**，
  因此不存在"绑定自己的点数"这回事。
- 真实的坑：`shutil.which("node")` 在本机找不到 Node（Node 只存在于
  `%USERPROFILE%\.workbuddy\binaries\node\versions\<ver>\node.exe`），
  报"未找到 Node.js 运行时"。修法是按 6 个位置依次找。
- 官方模型目录会轮换：旧的 `hy4free` 已下线，现有 14 个（`auto`/`hy4std`/`deepseek-v4-*`/
  `glm-5.3-flash`/…）。配置里存旧 id 会每次 400，所以要"保存时对齐目录"。
